# 0016. 숫자 출처를 결과 파일 옆 provenance.json에 저장

- 상태: 채택
- 날짜: 2026-11-16
- 관련: FR-21, #81

## 배경
excel_to_report_ppt가 만든 숫자가 AI가 지어낸 값이 아니라는 근거를 사용자가 직접 확인할 수 있어야 한다.
숫자마다 문서 위치와 원본 출처(시트·셀 범위·집계 방식)를 남겨야 하고, verify_numbers도 그 출처를 읽어
불일치 항목에 보여 줘야 한다. 샘플 엑셀처럼 부서 행이 번갈아 나오면 부서별 합계는 연속 범위의 단순 합으로
표현할 수 없다. 같은 입력이면 기록이 바이트 단위로 같아야 한다.

## 결정
결과 파일 옆 `<결과 파일 이름>.provenance.json`에 `{"numbers": [...]}`를 쓰고, 도구 결과의 `provenance`에
그 경로를 담는다. 출처는 `sum`·`sumif`·`count_distinct`·`share` 집계 방식과 열 하나의 연속 범위
(`range`, 필요하면 `criteria_range`·`criteria`)로 표현한다. 문서 위치는 저장된 pptx를 다시 읽어
슬라이드 파트 번호·도형 `cNvPr id`·그래프 파트/계열/점 idx로 찾는다. 집계에서 빠진 행(그룹 이름이나
값이 빈 행)이 있으면 `excluded_rows`에 행 번호를 남긴다. 그룹 이름은 `strip` 후 집계하므로
`sumif`·`count_distinct`에 `normalize: "strip"`을, 문서에 반올림해 보이는 합계에는 `digits`(소수
자릿수)를 남긴다. `share`는 합계가 0이면 0이다.

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
| --- | --- | --- | --- |
| pptx 안(커스텀 XML 파트)에 저장 | 파일 하나로 다닌다 | 사용자가 열어 보기 어렵고, 문서를 고치면 함께 바뀔 수 있다 | 사람이 직접 확인한다는 목적에 맞지 않는다 |
| SQLite 실행 로그에 저장 | 기존 저장소 재사용 | 결과 파일만 받은 사람은 볼 수 없다 | 문서와 출처가 따로 논다 |
| 숫자가 나온 셀 목록을 그대로 기록 | 집계 방식 없이 단순 | 비중·개수 같은 계산 숫자를 설명하지 못하고 파일이 커진다 | 집계 방식 4개로 모든 숫자를 설명할 수 있다 |
| 덱을 만들 때 도형 id를 예측해 기록 | 문서를 다시 읽지 않는다 | 엔진 구현에 따라 id가 바뀌면 틀린 위치가 남는다 | 저장된 문서에서 찾아야 위치가 사실이다 |

## 결과
- 사용자는 provenance.json의 범위와 집계 방식만으로 원본 엑셀을 다시 계산해 문서 숫자를 확인할 수 있다.
- 출처 기록에 실패하면(숫자가 든 도형을 못 찾는 등) 보고서를 내보내지 않고 `provenance` 단계 오류를 돌려준다.
- `file`은 도구에 넘긴 입력 경로를 그대로 쓴다. 같은 입력이면 같은 바이트가 나오지만, 다른 경로로 같은
  파일을 넘기면 기록도 달라진다.
- 머리글 이름이나 그룹 이름 앞부분에 든 숫자(예: "2024 매출")는 출처 대상이 아니다. 이런 입력이 실제로
  필요해지면 위치 기록 범위를 다시 본다.
